# Linux 内存管理入门（ARM Cortex-A AArch64）

> 本文面向嵌入式/系统开发初学者，默认以 **ARM Cortex-A 的 AArch64 架构**为例，先讲清「虚拟地址排布」，再讲「内核如何管理内存」，最后归纳「用户态使用内存的几种类型」。后续可在本目录按主题继续扩展（页表、slab、mmap、OOM、cgroup 内存等）。

## 0. 一句话总览

现代操作系统不让进程直接摸物理内存，而是给每个进程一个「假的、巨大的、连续的」虚拟地址空间，由 CPU 的 **MMU（内存管理单元）** 通过 **页表（Page Table）** 把虚拟地址翻译成物理地址。内核是这个翻译器的总设计师。

```
  进程虚拟地址            MMU + 页表              物理内存
 ┌─────────────┐       ┌──────────────┐        ┌──────────────┐
 │  虚拟地址 A   │ ───►  │  翻译/权限检查  │ ───►  │  物理页框      │
 │  虚拟地址 B   │       │  PGD→PUD→PMD→PTE │        │  页框 N        │
 └─────────────┘       └──────────────┘        └──────────────┘
```

好处：进程间隔离、每个进程看似独占大内存、按需分配（用到才映射）、换入换出（swap）等。

## 1. 虚拟地址排布（Virtual Address Layout）

### 1.1 虚拟地址 vs 物理地址

| 概念 | 说明 |
|------|------|
| 物理地址 | RAM 芯片上的真实地址，从 0 开始编号 |
| 虚拟地址 | 进程眼里看到的地址，与物理地址无关 |
| MMU | CPU 硬件，负责查页表完成翻译 |
| 页表 | 记录「虚拟页 → 物理页」映射和权限的数据结构 |
| TLB | 页表的高速缓存，加快翻译速度 |

内核把地址空间切成 **页（Page）**，常见页大小是 **4KB**。翻译不是逐字节的，而是逐页进行。

> **实操命令**：先跑起来看
> ```
> # 看自己这个进程（shell）的虚拟地址空间
> cat /proc/self/maps
>
> # 用户态可见的页大小（通常 4096，即 4KB）
> getconf PAGE_SIZE
>
> # 观察任意进程的地址空间布局
> pmap <pid>
> cat /proc/<pid>/maps | head -20
> ```

### 1.2 AArch64 的地址空间（48 位虚拟地址，4KB 页）

Linux 把地址空间分成两半：**低半是用户空间**，**高半是内核空间**。用户态进程只能访问低半，内核态可以访问全部。

```
 虚拟地址（AArch64，48位，4级页表，4KB页）
 ┌─────────────────────────────────────────────────────────────┐
 │ 0x0000_0000_0000_0000 ──────────────────────────────────┐      │
 │ │  用户空间（低 128 TB，0 ~ 0x0000_FFFF_FFFF_FFFF）      │      │
 │ │  ┌──────────────────────────────────┐                 │      │
 │ │  │  stack（栈，从高往低长）           │  ← 高地址        │      │
 │ │  │  ↓↓                            │                 │      │
 │ │  ├──────────────────────────────────┤                 │      │
 │ │  │  mmap 区域（共享库/匿名映射）      │  ← 向下长        │      │
 │ │  ├──────────────────────────────────┤                 │      │
 │ │  │  heap（堆，brk，从低往高长）       │  ← 向上长        │      │
 │ │  │  ↑↑                            │                 │      │
 │ │  ├──────────────────────────────────┤                 │      │
 │ │  │  data/BSS（已/未初始化全局变量）    │                 │      │
 │ │  ├──────────────────────────────────┤                 │      │
 │ │  │  text（代码段）                  │                 │      │
 │ │  └──────────────────────────────────┘                 │      │
 │ │  0x0000_0000_4000_0000（典型加载地址）                  │      │
 │ │  0x0000_0000_0000_0000（NULL，通常不可映射）             │      │
 │ └───────────────────────────────────────────────────────┘      │
 │ [ 空洞：不可访问 ]                                            │
 │ 0xFFFF_0000_0000_0000 ─────────────────────────────────┐        │
 │ │  内核空间（高 128 TB）                               │        │
 │ │  ┌──────────────────────────────────┐               │        │
 │ │  │  modules（内核模块区）             │               │        │
 │ │  ├──────────────────────────────────┤               │        │
 │ │  │  vmemmap（struct page 数组）       │               │        │
 │ │  ├──────────────────────────────────┤               │        │
 │ │  │  vmalloc 区域（非连续虚拟映射）      │               │        │
 │ │  ├──────────────────────────────────┤               │        │
 │ │  │  linear map 线性映射区（物理内存直接映射）│               │        │
 │ │  │  (PAGE_OFFSET 起点)              │               │        │
 │ │  └──────────────────────────────────┘               │        │
 │ └───────────────────────────────────────────────────────┘       │
 │ 0xFFFF_FFFF_FFFF_FFFF                                          │
 └─────────────────────────────────────────────────────────────┘
```

要点：

- **用户空间 0x0000_0000_0000_0000 ~ 0x0000_FFFF_FFFF_FFFF**：约 128 TB，每个进程各有一份「看起来一样」的布局，互不可见。
- **内核空间 0xFFFF_0000_0000_0000 ~ 0xFFFF_FFFF_FFFF_FFFF**：全局唯一，所有进程共享同一份内核页表。
- 中间约 128 TB 的空洞不可访问，用于隔离用户态与内核态，防止越界访问。
- 具体区段基址随内核配置与 KASLR 变化，可用 `/proc/kallsyms` 查看。

> **实操命令**：确认当前内核的地址空间配置
> ```
> # 页大小（AArch64 由编译选项决定，4KB/16KB/64KB）
> getconf PAGE_SIZE
>
> # 内核关键符号基址（KASLR 开启时每次启动都不同）
> grep -E " _text| _stext| _etext" /proc/kallsyms | head
>
> # 内存布局与保留区（内核视角）
> cat /proc/iomem | head -30
>
> # AArch64 页大小对应内核配置项（编译内核时二选一/三选一）
> #   CONFIG_ARM64_4K_PAGES
> #   CONFIG_ARM64_16K_PAGES
> #   CONFIG_ARM64_64K_PAGES
> ```

### 1.3 TTBR0 / TTBR1：用户态与内核态的分开页表

AArch64 的一个特色是内核通过两个页表基地址寄存器管理两套页表：

- **TTBR0** 指向**用户空间**页表（低地址，用户态运行、EL0 时使用）。
- **TTBR1** 指向**内核空间**页表（高地址，内核态、EL1 时使用）。

每次异常级别切换（用户态进入内核态 / 返回）时，硬件在 TTBR0 与 TTBR1 之间切换页表基址，同时用 **ASID（Address Space IDentifier，地址空间标识）** 区分不同进程的用户页表，避免频繁刷新 TLB：

```
  EL0（用户态）         EL1（内核态）
 ┌────────────┐       ┌────────────┐
 │  TTBR0     │ ──►   │  TTBR1     │
 │  当前进程   │       │  内核页表   │
 │  用户页表   │       │  (全局共享)  │
 └────────────┘       └────────────┘
     + ASID 区分进程        固定
```

### 1.4 页表层级（AArch64，4KB 页，4 级）

一次翻译要查多级页表。以 4KB 页、4 级页表为例（4 级 = PGD → PUD → PMD → PTE）：

```
 虚拟地址（64 位）
 ┌────────┬────────┬────────┬────────┬────────┬────────────┐
 │ 未使用  │  PGD   │  PUD   │  PMD   │  PTE   │  页内偏移    │
 │(高位)  │(9位)   │(9位)   │(9位)   │(9位)   │  (12位)     │
 └────────┴────────┴────────┴────────┴────────┴────────────┘
                  │        │        │        │
                  ▼        ▼        ▼        ▼
              PGD 表 ──► PUD 表 ──► PMD 表 ──► PTE 表 ──► 物理页框
```

- AArch64 支持多种页/层级组合：**4KB 页 + 4 级**（最常见）、**16KB 页 + 3 级**、**64KB 页 + 2~3 级**。
- 启用 52 位地址空间时可到 5 级（PGD → P4D → PUD → PMD → PTE），用于超大物理/虚拟寻址。
- 多级页表的意义：**不需要为整个地址空间建满表项**，只用到的区域才建立各级表，节省内存（按需分配）。
- 每级页表条目（Table Descriptor / Page Descriptor）带 **权限位（读/写/执行）、用户/内核位（AP）、写时复制位、脏位、存在位** 等；内核通过 `pgtable-*.h` 与 `struct page` 管理这些页表页本身。

> **实操命令**：看页表内存开销
> ```
> # 内核页表占用的物理内存（/proc/meminfo 的 KernelPageTables）
> grep -iE "pagetables|page_tables" /proc/meminfo
>
> # 当前页大小与虚拟地址位数
> getconf PAGE_SIZE
> # ARM64 默认 48 位 VA；开启 LVA 可达 52 位
> ```

## 2. 内核如何管理内存

内核管内存分三个层次：**物理内存怎么分**、**虚拟内存怎么映射**、**分配 API 有哪些**。这部分与架构基本无关，AArch64 上同样适用。

### 2.1 物理内存的组织：Node / Zone / Page

```
 物理内存
 ┌──────────────────────────────────────────────┐
 │  NUMA 节点 Node 0          NUMA 节点 Node 1    │
 │  ┌────────────────────┐   ┌────────────────┐  │
 │  │ DMA 区（低端，外设用）│   │  ...            │  │
 │  ├────────────────────┤   │                │  │
 │  │ Normal 区（普通内存） │   │                │  │
 │  ├────────────────────┤   │                │  │
 │  │ Movable 区（可回收） │   │                │  │
 │  └────────────────────┘   └────────────────┘  │
 └──────────────────────────────────────────────┘
```

- **Node（节点）**：对应一个 CPU 与本地内存的 NUMA 单元；单核 / 大部分嵌入式 SoC（如全志、瑞芯微 Cortex-A 平台）只有一个 Node。
- **Zone（区）**：按用途划分：`DMA`（低地址，外设 DMA 可用）、`Normal`（普通）、`Movable`（可移动/可回收，利于内存规整、防碎片）。
- **Page（页）**：最小物理内存单元（通常 4KB），内核用 `struct page` 描述每一页。

> **实操命令**：看 Node / Zone 划分
> ```
> # 各 NUMA 节点的内存概况
> cat /sys/devices/system/node/node*/meminfo
>
> # 每个 Zone 的详细统计（pages_free / active / inactive / steal 等）
> cat /proc/zoneinfo | head -60
>
> # 每 Zone 各 order 空闲块（见 2.2）
> cat /proc/buddyinfo
> ```

### 2.2 页分配器：伙伴系统（Buddy System）

物理页分配使用 **伙伴系统**，把空闲页按 2 的幂组织成链表（order 0 ~ order 10，即 1 页 ~ 1024 页）：

```
 order:   0     1     2     3     ...
         [4K] [8K]  [16K] [32K]
         空闲链表: 0→[][][]
                   1→[][]
                   2→[ ]
```

- 申请 n 页时，向上取整到 2 的幂；没有刚好大小的块就**拆大块**，释放时**合并相邻的伙伴块**。
- 好处是分配/释放速度快、碎片控制较好；缺点是粒度固定（都是 2 的幂）。

> **实操命令**：看伙伴系统的空闲块
> ```
> # 每行一个 Zone，每列对应 order 0~10 的空闲块数量
> # 例如 "Node 0, zone Normal:  10 20 15 8 3 0 ..." 即 order0=10 块、order1=20 块...
> cat /proc/buddyinfo
>
> # 更细：按页类型（Unmovable/Reclaimable/Movable）看分配情况
> cat /proc/pagetypeinfo | head -40
>
> # 连续空闲块是否充足，可直接判断能否分配大页/大块（见 3.5）
> # 若 order>=9 全为 0，说明碎片严重，分配 2MB 大页会失败
> ```

### 2.3 面向小对象的分配：slab / slub

内核里大量对象很小（如 `task_struct`、`inode`），按 4KB 整页分配太浪费。于是用 **slab/slub 分配器**：先申请若干页，再切成等大小的对象缓存（cache），重复使用并带类型元信息。

- `kmalloc` / `kfree`：通用的小内存分配（底层走 slab）。
- `kmem_cache_create`：为某种结构体建立专用缓存，提升效率。

> **实操命令**：看 slab 缓存占用
> ```
> cat /proc/slabinfo | head          # 每个 cache：对象数、使用率、每对象大小
> slabtop                            # 交互式，按占用排序，找出最占内存的 cache
>
> # 统计 slab 总占用
> grep -iE "^slab|SReclaimable|SUnreclaim" /proc/meminfo
> ```

### 2.4 虚拟内存映射：kmalloc vs vmalloc

| API | 物理连续？ | 虚拟连续？ | 适用 |
|-----|-----------|-----------|------|
| `kmalloc` / `kzalloc` | 物理连续 | 虚拟连续 | 需要 DMA、外设寄存器的小块内存 |
| `alloc_pages` | 物理连续 | 虚拟连续 | 整页分配 |
| `vmalloc` / `vfree` | 物理**不**连续 | 虚拟连续 | 大块、不要求物理连续（如临时大数据缓冲） |
| `kmem_cache_*` | 物理连续 | 虚拟连续 | 同构对象缓存 |

```
 物理页（可能散落各处）          虚拟地址（连续）
 ┌────┐  ┌────┐  ┌────┐        ┌───────────────┐
 │ 页A │  │ 页B │  │ 页C │ ──►   │ vmalloc 区     │
 └────┘  └────┘  └────┘        │ 连续虚拟地址    │
                               └───────────────┘
```

> **实操命令**：看 vmalloc 谁在用（需 root）
> ```
> cat /proc/vmallocinfo | head
> # 每行：起始地址-结束地址 | 大小 | 分配者（模块/调用路径）
>
> # 哪些模块占用的 vmalloc 最多
> cat /proc/vmallocinfo | awk '{print $2, $3}' | sort -rn | head
> ```

### 2.5 页表、TLB 与缺页处理

- 进程/内核首次访问某虚拟地址时，页表里往往还没有映射，CPU 触发 **缺页异常（page fault）**，内核现场建立映射（或决定 OOM）。
- **按需分配（demand paging）**：malloc 返回的地址一开始并不真正占用物理内存，只有真正写入时才缺页分配，所以 `malloc` 大内存往往「看起来成功了」。
- 翻译结果缓存进 **TLB**。AArch64 上通过 **ASID** 区分进程，进程切换时无需完全刷 TLB，只在必要时执行 `TLBI` 指令使特定条目失效。

> **实操命令**：观察缺页（page fault）
> ```
> # 看某进程累计的 minor/major 缺页数
> ps -o pid,min_flt,maj_flt,vsz,rss,cmd -p <pid>
> cat /proc/<pid>/stat | awk '{print "min_flt="$10, "maj_flt="$12}'
>
> # 跑一个程序，看它触发了多少缺页
> time -v ./your_prog 2>&1 | grep -iE "fault|RSS"
>
> # 系统层面每秒缺页/切换统计
> vmstat 1
> ```
> 小实验：启动一个 shell，`cat /proc/self/stat` 记下 `min_flt`，再连续 `ls` 几次后重读，minor fault 会明显增长——缺页几乎无时无刻不在发生。

### 2.6 内存压力与回收

当物理内存紧张时，内核会：

- **回收（reclaim）**：回收匿名页（写回 swap）、文件缓存页（写回磁盘/丢弃）。
- **swap 交换**：把不常用的匿名页换到磁盘。
- **内存压缩 zswap**：先压缩再换出，减少 IO。
- **大页 HugePage / THP**：用 2MB/1GB 大页减少页表开销、提高 TLB 命中。
- **OOM Killer**：实在无内存可用时，按分值杀掉占用大的进程（`oom_score`），并记录到 `dmesg`。

> **实操命令**：制造内存压力，观察回收 / swap / OOM
> ```
> # 1) 打开 swap（先建好分区/文件）
> mkswap /dev/xxx && swapon /dev/xxx
> cat /proc/swaps                      # 查看已启用 swap
>
> # 2) 观察回收与交换计数
> cat /proc/vmstat | grep -E "pgfault|pgmajfault|pswpin|pswpout"
> #   pswpin/pswpout 增长 = 正在换入换出；pgmajfault 增长 = 频繁走磁盘
>
> # 3) 内存压力指数（PSI，0~100%，越高越吃紧）
> cat /proc/pressure/memory
>
> # 4) 看是否发生过 OOM
> dmesg | grep -iE "oom|killed process"
>
> # 5) 手动制造压力：分配并写满约 90% 内存（用 3.1 的压测程序），
> #    边跑边用 vmstat 1 / free -h 观察 Available 与 swap 变化
> ```

### 2.7 常用查看手段

```
# 物理内存概况
cat /proc/meminfo
free -h

# 每个进程虚拟内存 / 真实占用
pmap <pid>
cat /proc/<pid>/maps      # 虚拟地址区间与权限
cat /proc/<pid>/smaps     # 更细：每区 RSS/PSS/共享/私有
cat /proc/<pid>/status    # VmPeak/VmSize/VmRSS 等

# 内存碎片 / 伙伴系统状态
cat /proc/buddyinfo
cat /proc/pagetypeinfo

# 系统级内存动态
vmstat 1
cat /proc/vmstat          # pgfault/pgmajfault/pswpin/pswpout 等计数

# 内存压力（PSI）
cat /proc/pressure/memory

# 页缓存/匿名/交换汇总
grep -E "^Cached|^AnonPages|^SwapCached|^SwapTotal|^SwapFree|^HugePages_Total" /proc/meminfo
```

## 3. 用户态使用内存的几种类型

用户态进程使用内存，本质上都是「向内核申请映射」。按**映射内容与共享性**可归纳为以下几种类型。下面重点展开 **匿名内存** 与 **大页内存** 的底层机制，其余类型讲清原理与对比。

### 3.1 匿名内存（Anonymous Memory）

内容不来自文件、不与磁盘对应、通常是私有的。典型来源：

- **堆（heap）**：`malloc`/`calloc`/`realloc`（glibc 内部用 `brk/sbrk` 或 `mmap`）。
- **栈（stack）**：局部变量、函数调用帧。
- **`mmap(MAP_ANONYMOUS)`**：大块匿名映射（glibc 对超过 `MMAP_THRESHOLD` 的大 malloc 直接走这个）。

#### 3.1.1 底层结构：VMA + mm_struct

每个进程地址空间由 `mm_struct` 描述，其中维护一段段 **VMA（Virtual Memory Area，虚拟内存区）**，每个 VMA 描述一段「起始地址 + 长度 + 权限 + 映射类型」的连续区域。`/proc/<pid>/maps` 里的每一行就是一个 VMA。

```
 进程 mm_struct
 ┌────────────────────────────────┐
 │  mmap 链表 / 红黑树             │
 │  ├── VMA [heap]    rw- 匿名     │
 │  ├── VMA [libc.so] r-x 文件     │
 │  ├── VMA [mmap]    rw- 匿名     │
 │  └── VMA [stack]   rw- 匿名     │
 └────────────────────────────────┘
```

#### 3.1.2 按需分配（demand paging）才是关键

`malloc` 只是 **保留了一段虚拟地址**（建 VMA），**并没有立刻占用物理内存**。直到进程真正读/写某个页，MMU 找不到对应物理页而触发 **缺页异常**，内核才去分配物理页并填页表：

```
 malloc(n)                       首次访问
 ─────────                        ─────────
 建立 VMA（只占虚拟空间）  ──►   触发缺页 ──► 内核分配物理页 ──► 填 PTE ──► 继续执行
 不分配物理页                       ↑ 这才真正消耗 RSS
```

这就是为什么 `malloc` 很大的内存（如 1GB）常常「成功」，但访问到一半进程可能被 OOM 杀掉——因为物理内存是现用现给。

#### 3.1.3 glibc malloc 的两种后盾：brk 与 mmap

| 手段 | 系统调用 | 特点 | 触发 |
|------|---------|------|------|
| 堆扩展 | `brk`/`sbrk` | 调整 program break，扩大 heap VMA，低开销、**物理连续（虚拟连续）** | 小块分配（默认阈值内） |
| 大块映射 | `mmap(MAP_ANONYMOUS, MAP_PRIVATE)` | 每次分配新建独立 VMA，可按页对齐、天然对齐 | 超过 `MMAP_THRESHOLD`（默认 128KB） |

glibc 的 `MMAP_THRESHOLD` 是动态的，会根据历史行为调整，避免大量小对象反复 mmap/munmap 造成 TLB 抖动。

#### 3.1.4 观察与边界

```
# smaps 里的 Anonymous 字段 = 真正占用的匿名物理内存
grep -A 5 heap /proc/<pid>/smaps
Rss:              40 kB          # 该区当前占用物理
Private:          40 kB
Anonymous:        40 kB          # 匿名内存标识

# 虚拟地址空间上限（RLIMIT_AS）
ulimit -v

# 内核过度承诺策略（决定 malloc 可不可超卖）
cat /proc/sys/vm/overcommit_memory   # 0=启发式 1=总是允许 2=禁止超卖
```

> **栈也是匿名内存**：它由内核在进程创建时建立 VMA，向下增长，访问越界时触发栈增长缺页（超过 `ulimit -s` 则 SIGSEGV）。

> **实操命令**：亲手验证 demand paging（强烈推荐）
> ```
> # 1) 写一个程序：malloc 1GB 但不写，再写满
> cat > /tmp/t.c <<'EOF'
> #include <stdio.h>
> #include <stdlib.h>
> #include <string.h>
> #include <unistd.h>
> int main(void){
>     size_t n = 1UL<<30;            // 1GB
>     char *p = malloc(n);
>     printf("malloc ok, pid=%d, sleep (此时 RSS 应很小)\n", getpid());
>     sleep(8);
>     memset(p, 0xAA, n);            // 真正访问 -> 触发缺页
>     printf("touched all, sleep\n");
>     sleep(8);
>     return 0;
> }
> EOF
> gcc /tmp/t.c -o /tmp/t
>
> # 2) 另开终端，在两个 sleep 窗口分别执行：
> pmap $(pgrep -f /tmp/t) | tail -1
> #   第一次（malloc 后未写）：VSZ 约 1G，RSS 很小
> #   第二次（写满后）      ：RSS 猛增到接近 1G —— 证明内存是“用才给”
>
> # 3) 同时观察缺页
> ps -o pid,min_flt,maj_flt,cmd -p $(pgrep -f /tmp/t)
> ```

### 3.2 文件映射内存（File-backed Memory）

虚拟页背后对应一个文件，用 `mmap` 把文件映射进地址空间：

- 加载可执行文件（`.text`、`.data` 段映射自 ELF 文件）。
- 动态链接库 `.so` 的代码段、数据段。
- 业务场景：读写大文件、把文件当数组访问。

**与 read/write 的区别**：

```
 read/write：数据先经内核 page cache，再拷贝到用户缓冲（两次拷贝）
 mmap：      直接映射内核 page cache，用户访问同一物理页（零拷贝）
```

特点：

- 缺页时从**文件**读入，**可回收**（内存紧张时直接丢弃，再从文件重建，无需写 swap）。
- 多个进程映射同一文件时**共享物理页**（共享库的代码段天然共享，节省内存）。
- 写入回文件由内核回写（`writeback`）或用户 `msync` 控制。

```
# 识别：maps 里带文件路径的行即文件映射
grep -E "\.so|\.bin|/data" /proc/<pid>/maps
```

> **实操命令**：看文件页缓存（page cache）
> ```
> # 文件被 mmap/read 后会在物理内存留缓存
> grep -E "^Cached|^AnonPages|^Dirty" /proc/meminfo
>
> # 查看某个具体文件被缓存了多少（vmtouch 需另装）
> vmtouch /path/to/bigfile
>
> # 主动清缓存（需 root，仅实验用，会拖慢后续 IO）
> sync; echo 3 > /proc/sys/vm/drop_caches
> ```

### 3.3 共享内存（Shared Memory）

显式让多个进程共享同一物理页：

- **SysV 共享内存**：`shmget` / `shmat`（挂载于 `/dev/shm`）。
- **POSIX 共享内存**：`shm_open` + `mmap(MAP_SHARED)`。
- **mmap 文件 + MAP_SHARED**：多个进程映射同一文件可互见修改。

用于进程间通信（IPC），比管道/消息队列更快（**无内核拷贝**，双方直接访问同一物理页）。

```
# 查看系统共享内存
ipcs -m
ls -l /dev/shm

# 看某进程用了多少共享内存（SHR / Shared 字段）
cat /proc/<pid>/smaps | grep Shared
```

> **PSS（Proportional Set Size）**：共享页按共享进程数均摊，用于准确估算「一个进程实际贡献了多少物理内存」。`smaps` 里的 `Pss` 字段即此值。

> **实操命令**：创建并查看共享内存
> ```
> # 建一个 1MB 的 POSIX 共享对象
> dd if=/dev/zero of=/dev/shm/demo bs=1M count=1
>
> # 或 SysV 方式：创建 / 查看 / 删除
> ipcmk -M 1048576         # 分配 1MB 共享内存
> ipcs -m                  # 查看 key/id/owner/size
> ipcrm -m <id>            # 按 id 删除
>
> # 系统共享内存总限额
> ipcs -l
> ```

### 3.4 按共享/私有维度的归类（MAP_SHARED vs MAP_PRIVATE）

| 维度 | 值 | 含义 |
|------|----|------|
| 映射内容 | 匿名 | 内容只来自内存，换出写 swap |
| 映射内容 | 文件 | 内容来自文件，可回收自文件重建 |
| 共享性 | `MAP_PRIVATE` | 私有，**写时复制（COW）**：写时复制一份，不污染原映射/文件 |
| 共享性 | `MAP_SHARED` | 共享，写直接落到底层文件或共享区，多进程互见 |

**写时复制（COW）** 是 `fork` 和 `MAP_PRIVATE` 的基石：

```
 fork 之后：父子共享同一物理页（PTE 标记为只读 + COW）
 某方要写  ──►  触发 COW 缺页 ──► 内核复制一份物理页 ──► 写进程指向新页
```

- 好处：`fork` 极快（不拷贝物理内存）、内存极大节省（读多写少场景）。
- 代价：首次写时会多一次缺页复制（写放大）。

> **实操命令**：验证 COW
> ```
> # 编译一个 fork 后父子各自写数据的程序：
> #   fork 刚返回：父子 RSS 相近（共享同一物理页，页面标记只读+COW）
> #   父子各自写入：各自触发 COW 缺页复制，RSS 双双增长
> pmap <pid> | tail -1
>
> # 观察 smaps 的 Private 字段是否随写入变大
> grep -E "Private|Pss" /proc/<pid>/smaps | head
> ```

### 3.5 大页内存（Hugepage）—— 重点展开

普通页 4KB，映射 1GB 内存需要 256K 个 PTE、页表本身占约 2MB；且 4KB 粒度导致 **TLB 命中率低**。大页用 **2MB / 1GB** 一次映射一大块，把页表与 TLB 开销大幅压缩：

| 页大小 | 页表级 | 映射 1GB 的 PTE 数 | 页表内存 | TLB 命中 |
|--------|--------|-------------------|---------|---------|
| 4KB | PTE（第4级） | 262144 | ~2MB | 低 |
| 2MB | PMD（第3级） | 512 | ~4KB | 高 |
| 1GB | PUD（第2级） | 1 | ~几B | 最高 |

#### 3.5.1 静态大页 hugetlb（显式预留）

需要提前预留物理内存（**启动参数或运行时预留**），之后由进程显式申请：

```
# 运行时预留（示例预留 10 个 2MB 大页）
echo 10 > /proc/sys/vm/nr_hugepages

# 或用启动参数
hugepages=10 hugepagesz=2M

# 查看预留情况（/proc/meminfo 的 HugePages_* 字段）
cat /proc/meminfo | grep Huge
HugePages_Total:      10
HugePages_Free:       10

# 系统层面配置目录
ls /sys/kernel/mm/hugepages/hugepages-2048kB/
```

进程申请方式：

```
# mmap 大页（须带 MAP_HUGETLB）
mmap(NULL, len, PROT_READ|PROT_WRITE,
     MAP_SHARED|MAP_HUGETLB, fd, 0);

# SysV 共享内存大页
shmget(key, size, IPC_CREAT|SHM_HUGETLB);

# 挂载 hugetlbfs 用文件方式访问
mount -t hugetlbfs none /mnt/huge
```

优点：**预分配保证不碎片化、不被换出、TLB 命中高**；缺点：内存被预留后别处不可用、申请不到就失败。

> **实操命令**：预留并验证大页
> ```
> # 预留 8 个 2MB 大页（需 root）
> echo 8 > /proc/sys/vm/nr_hugepages
> grep Huge /proc/meminfo
> #   HugePages_Total 应立即为 8，HugePages_Free 为 8
>
> # 查看本内核支持哪些大页尺寸目录
> ls /sys/kernel/mm/hugepages/
>
> # 用 hugetlbfs 快速验证可申请
> mount -t hugetlbfs none /mnt/huge
> dd if=/dev/zero of=/mnt/huge/f bs=2M count=1
> ```

#### 3.5.2 透明大页 THP（Transparent Huge Pages）

无需显式申请，内核**自动**尝试把连续的 4KB 页合并成 2MB 大页，对进程透明：

```
# 策略：always / madvise / never
cat /sys/kernel/mm/transparent_hugepage/enabled

# 进程级提示用 madvise（need THP 的映射才启用）
madvise(addr, len, MADV_HUGEPAGE);     # 提示启用
madvise(addr, len, MADV_NOHUGEPAGE);   # 提示关闭
```

- **always**：所有匿名内存都可能被合并成 THP。
- **madvise**：只有显式 `madvise(MADV_HUGEPAGE)` 的区域才合并（推荐，避免内存占用膨胀）。
- **never**：关闭。

THP 的坑：合并前需要找**连续的物理页**，在碎片化严重时合并失败或触发内存规整（`compact`），可能引入瞬时延迟；且大页一旦只用了其中一页也会整块占用（内存膨胀）。数据库等场景常用 `madvise` 精确控制。

> **实操命令**：查看/切换 THP 策略
> ```
> cat /sys/kernel/mm/transparent_hugepage/enabled
> #   输出形如 [always] madvise never（[] 标注当前值）
> echo madvise > /sys/kernel/mm/transparent_hugepage/enabled   # 需 root
>
> # 查看 THP 已合并多少页、扫描频率
> cat /sys/kernel/mm/transparent_hugepage/khugepaged/pages_collapsed
> cat /sys/kernel/mm/transparent_hugepage/khugepaged/scan_sleep_millisecs
> ```

#### 3.5.3 如何观察进程是否用了大页

```
# smaps 里出现 huge 标注 / THP 字段
grep -i -E "huge|thp" /proc/<pid>/smaps

# 系统 THP 统计
cat /sys/kernel/mm/transparent_hugepage/khugepaged/pages_collapsed
```

### 3.6 锁定内存（Locked / mlock）

`mlock`/`mlockall` 把页锁在物理内存中，**禁止换出**：

```
mlock(addr, len);              # 锁一段
mlockall(MCL_CURRENT|MCL_FUTURE); # 锁当前及未来所有
# 查看
grep VmLocked /proc/<pid>/status
```

- 用于对延迟敏感、不能容忍缺页的场合（实时、密码学密钥材料、DMA 缓冲）。
- 会挤占内存，过量使用有 OOM 风险；`ulimit -l` 限制可锁内存上限。

> **实操命令**：查看锁定内存限制与占用
> ```
> ulimit -l                              # 单进程可锁内存上限（KB）
> grep -i "^Locked" /proc/meminfo        # 系统当前已锁定量
> grep VmLocked /proc/<pid>/status       # 某进程锁定量
> ```

### 3.7 汇总表

| 类型 | 内容来源 | 是否换出 | 底层机制/分配 | 典型场景 |
|------|---------|---------|--------------|---------|
| 匿名内存（堆/栈/mmap 匿名） | 内存 | 写 swap | VMA + 按需缺页；brk 或 mmap | malloc、局部变量、大缓冲 |
| 文件映射内存 | 文件 | 从文件重建，不写 swap | page cache + mmap | 可执行文件、.so、大文件 IO |
| 共享内存 | 内存/文件（MAP_SHARED） | 视实现 | 共享物理页（无内核拷贝） | IPC、多进程共享数据 |
| 大页 hugetlb（静态预留） | 内存 | 一般不换出 | 预分配 PMD/PUD 级映射 | 数据库、大数据、性能敏感 |
| 大页 THP（透明） | 内存 | 一般不换出 | 内核自动合并 4KB→2MB | 匿名内存自动加速 |
| 锁定内存（mlock） | 内存 | 禁止换出 | PTE 置「不可换出」位 | 实时、密钥、DMA |

### 3.8 判断一个进程用了哪些类型

```
# 看 maps：权限与文件名能大致判断
cat /proc/<pid>/maps

# 各区间更细：RSS/PSS/Shared/Private/Anonymous/swap
cat /proc/<pid>/smaps | head -60
```

- `[heap]`、`[stack]`、`[anon]` 标签 → **匿名内存**；
- 带文件路径（`.so`、`.bin` 等）→ **文件映射**；
- 带 `/dev/shm` 或 `shmem` → **共享内存**；
- 出现 `huge` / `THP` 标注 → **大页**。
